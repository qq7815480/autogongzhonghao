# 参考文章写作规范

## 核心原则

**参考文章是"原料"不是"模板"。**

当用户给了参考文章（无论一篇还是多篇），目标是创作一篇读起来像"老孙/豌豆四喜写的"文章，而不是"两篇文章的总结"。

## 绝对不能做的事

| 错误做法 | 为什么错 |
|---|---|
| 跟着参考文章的结构走（小节划分、标题顺序） | 读者一眼看出是整合 |
| 原文复制任何句子或段落（哪怕换几个词） | 这是洗稿，不是创作 |
| 做"两篇文章的总结/整合" | 读完觉得"这是总结"→ 失败 |
| 用参考文章里的小众案例（专有项目名、小众工具名） | 读者不熟悉，缺乏代入感 |
| 用具体时间点（"上周三下午"） | 让读者觉得是旧闻，不是最近发生的 |
| 用参考文章里的专业术语原文 | 普通读者看不懂 |

## 必须做到的事

1. **提取素材**：从参考文章中提取核心数据、独特案例、关键观点、有价值的引用
2. **丢掉结构**：不看原文的小节划分，自己重新组织文章骨架
3. **用自己的话讲**：所有内容必须用自己的句式重新表达，不是"换个说法"而是"重新讲述"
4. **加入"我"**：必须有自己的判断、经历、踩坑、困惑 —— 这是区分"总结"和"创作"的关键
5. **必须问用户**：你对这个话题有什么亲历的细节？踩过什么坑？有什么判断是别人没说过的？

## 文章细节规范

### 时间处理
- ❌ "上周三下午 4 点"
- ✅ "最近"、"今天"、"前几天"

### 案例替换
- ❌ `huashu-design`（小众开源项目）
- ✅ 微信、Python、API、GitHub（大众熟悉的）

### 术语替换
- ❌ "Claude Opus 4.7"、"GPT-5.5"
- ✅ 用读者能看懂的通用描述，或者加简短解释

## 判断标准

| 读者感受 | 结果 |
|---|---|
| "这是两篇参考文章的总结" | ❌ 失败 |
| "这是老孙/豌豆四喜写的" | ✅ 成功 |

## 用户反馈的常见问题

1. **"只是整合/总结"**：没有加入"我"的视角和判断，结构跟参考文章一样
2. **"案例太小众"**：用了参考文章里的专有名词，换成大众熟悉的
3. **"时间太具体"**：用了具体时间点，让读者觉得是旧闻
4. **"术语看不懂"**：参考文章里的专业术语没替换
5. **⛔ "摘要/文章太长了"**：改写后的文章比参考文章还长（3800字 vs 3000字原文）。**必须控制在参考文章字数的 ±10% 以内**。超出即为"扩写"，不合格。写完后估算字数，超了就删减
6. **"先不要配图"**：写完文章后必须先给用户看，等用户确认内容没问题后再生成配图和封面

## 工作流程

```
收到参考文章
    ↓
提取素材（数据、案例、观点）  ← 从参考文章来
    ↓
丢掉原文结构                 ← 不跟着参考文章的小节走
    ↓
问用户要细节                 ← "你对这个话题有什么亲历的？踩过什么坑？"
    ↓
用自己的视角重新组织           ← 不是整合，是创作
    ↓
加入"我"的判断和经历          ← 区分"总结"和"创作"的关键
    ↓
检查细节规范                 ← 时间、案例、术语是否符合规范
    ↓
读者觉得"这是老孙写的" ✅
```
